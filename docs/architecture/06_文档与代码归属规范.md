# 1. 归属判断表

| 内容 | 应该放在哪里 | 说明 |
|---|---|---|
| 平台总体架构 | `docs/architecture/` | 只描述"整个平台怎么运行" |
| Agent Runtime 设计 | `docs/architecture/01_Agent_平台架构.md` 引用；实现细节进技术设计 | Runtime 是 Platform 能力 |
| LLM Gateway 契约 | `docs/architecture/02_共享基础设施规范.md` 引用 | 全平台唯一契约来源 |
| 某个 Agent 的产品设计 | `docs/projects/<Project>/产品定义.md` | 不含 Java 类名 / 字段 / API |
| 某个 Agent 的技术设计 | `docs/projects/<Project>/技术设计.md` | 必须引用 Platform 文档 |
| 某个 Agent 的 System Prompt | `docs/projects/<Project>/Prompt设计.md` | 必须可版本化 |
| 多个 Agent 共用的 Prompt 片段 | `docs/projects/<Project>/Prompt设计.md` 内标注 shared 段；确属跨 Project 时上移为 Platform 能力 | 不新建独立顶层目录 |
| 数据库公共设计（DDL） | 各 Project `技术设计.md` 持有各自表；跨 Project 公共模型在 DOCUMENTATION_RULES §21 清单中登记唯一来源 | 公共表只允许一个 DDL 权威来源 |
| 某 Project 特有的数据模型 | `docs/projects/<Project>/技术设计.md` | 通过 project_id 隔离 |
| 公共 LLM Gateway 代码 | `com.aigamelab.llm`（Platform 包） | 见 §2 |
| 某 Agent 专用 Tool | 该 Project 的 Java 包内（未来 `agents/<project>/tool/`） | 注册到统一 ToolRegistry |
| 通用 Tool | Platform tool 包 | 所有 Agent 可复用 |
| 实验数据 / 运行数据 | `data/`（已 gitignore） | 统一 agl.db，禁止分库 |
| 自动测试结果 | 本地构建产物（gitignore）；持久化测试结果入 agl.db 对应表 | 禁止提交到 Git |
| 技术债 | `docs/state/tech-debt.md`（全项目唯一登记处） | task-state.md 只放活跃 Sprint 摘要 |
| 已废弃设计 | `docs/archive/`（已创建） | git 不跟踪空目录 |
| 当前开发任务状态 | `docs/state/task-state.md` | 唯一进度事实来源 |
| 架构重大决策 | `docs/decisions/ADR-xxx.md`（首次决策时创建） | 背景/选项/决策/原因/后果 |
| 跨 Project 调用规范 | `docs/architecture/03_Agent_之间协作规范.md` | 见本文档 §4 |

# 2. 代码包归属规则

原则：**Agent 可以依赖 Platform，Platform 不能依赖具体 Agent。**

```text
正确：
GameDesignerAgent → AgentRuntime → LlmGateway → DeepSeek

禁止：
LlmGateway → GameDesignerAgent
```

当前后端包结构（第一阶段实际状态）：

| 包 | 层级 | 职责 |
|---|---|---|
| `common/` `config/` `domain/` `repository/` `api/` `event/` `llm/` `runtime/` `tool/` | Platform（共享基础设施） | 所有 Project 共用 |
| 未来 `agents/<project>/` | Project | 具体 Agent 的业务逻辑 |

## 迁移方案（不在本 Task 执行）

当前平铺包结构是 P0/P1 Sprint 的既定产物且正被并发使用。未来引入第二个 Project（Tester 业务代码）时，通过独立 Task 执行包结构重组：

- Platform 包收拢到 `platform/`（或维持平铺，以当时 ADR 为准）
- 各 Agent 业务进入 `agents/<project>/`
- 移动前必须验证 Spring Component Scan 与 Maven 模块识别不受影响

在此之前**禁止为了目录美观移动任何 Java 代码**。

# 3. Project 目录标准

新 Project 一律从 [../projects/PROJECT_TEMPLATE/](../projects/PROJECT_TEMPLATE/) 复制开始，按 [DOCUMENTATION_RULES.md](DOCUMENTATION_RULES.md) §7 的标准结构组织，只创建真正需要的文件，禁止创建空文档。

---

# 4. 跨 Project 调用规则

第一阶段规范（不提前实现）：

```text
允许：
ProjectA → Platform Interface（Runtime / Tool / Event / Artifact）→ ProjectB 能力

禁止：
ProjectA → HTTP → ProjectB（第一阶段无多服务）
ProjectA → import ProjectB 内部 Java Class
```

需要共享的能力优先上移到 Platform（见 [DOCUMENTATION_RULES.md](DOCUMENTATION_RULES.md) §24–25）。

---

# 5. 数据库与服务原则

- 一个 SQLite：`data/agl.db`，所有 Project 共享，靠 `project_id` 隔离。禁止 designer.db / tester.db 分库。
- 一个 Backend + 一个 Frontend：不同 Project 只是不同模块/API 前缀，不是不同服务。
- 依据：[05_部署与运行架构.md](05_部署与运行架构.md)、[ARCHITECTURE_RULES.md](ARCHITECTURE_RULES.md) Rule 8/9、DOCUMENTATION_RULES §26–28。
