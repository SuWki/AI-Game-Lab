# 已有游戏分析与改进：产品设计

层级：Architecture。2026-11-12 按用户目标补充。本文定义长期产品方向与职责；实现状态以 [task-state](../state/task-state.md) 为准，接口以 Platform 文档为准。

> 范围修正：本文是“已有游戏改进”专项设计。Lab 同时包含同类型新游戏的设计制造能力，整体定位以 [产品总设计](GAME_LAB_PRODUCT_DESIGN.md) 为准，新作流程见 [生产契约](../platform/GAME_PRODUCTION_CONTRACT.md)。

## 1. 定位与价值判断

AI Game Lab 帮助开发者围绕已有游戏完成问题分析、可复现测试、优化和受控功能扩展。主要使用者是需要持续迭代自己游戏的个人开发者与小团队；商业成品游戏的观察分析是后续场景。

本设计判断是：代码生成越容易，平台越应积累可验证的游戏知识——哪个版本在什么条件下发生问题，修改解决了什么，又损害了什么。模型负责提出假设与实现候选方案，平台负责连接项目、运行实验、保存证据和支持人类判断。模型能力增强可以提升这条流程的效率，但不会自动证明实验正确、玩法改善或目标达成。

近期价值假设：用户能更快得到可复现问题和可信修改，并在下一版本重复使用既有测试。该假设尚未由真实用户长期使用验证；自动化测试数量与 Agent 数量不能证明它成立。

## 2. 四类任务与交付物

| 用户任务 | 必要输入 | 最小交付 | 达成标准 |
|---|---|---|---|
| 分析游戏 | 版本/可访问材料、具体疑问 | 观察事实、解释假设、缺失信息、验证建议 | 每个事实有来源；未经验证的因果解释明确标为假设 |
| 发现与复现问题 | 可运行目标、场景、预期行为 | 复现步骤或动作记录、实际/预期差异、证据 | 同条件可复跑；失败或不稳定被如实记录 |
| 优化已有行为 | 问题或指标、基线、允许改动范围 | 改动方案、前后对照、收益与退化 | 预先约定的指标改善且必要回归通过；小样本不下总体结论 |
| 扩展功能 | 行为规格、边界与兼容要求 | 修改差异、新功能验收、旧功能回归 | 新需求通过并保留已有能力；验证结果可人工复核 |

“分析完成”“命令执行完”“测试通过”“改进达标”“人类接受”是不同结论。性能、数值平衡和主观体验也需不同证据，不能统一折算成一个 PASS。

## 3. 接入能力与产品范围

| 接入方式 | 能力 | 结论边界 |
|---|---|---|
| 自有源码 + 测试命令 | 构建、逻辑测试、源码提案与回归 | 首个可用版本的主要范围；不默认具有逐帧观察能力 |
| 可交互引擎/浏览器适配 | 操作、状态观察、动作重放 | 按适配器声明能力；夹具强制场景与自然游玩分开报告 |
| 第三方成品 + 录像/日志/可用操作接口 | 观察、记录问题、分析机制、提出建议 | 无内部状态时因果判断有限；没有源码/Mod 接口时不承诺内部修改 |

接入能力须显式声明，缺能力时交付分析或缺证据结论。命令测试是有效入口；只有任务确需动作/状态控制时才增加交互适配，不强制所有游戏实现相同战斗模型。

本专项优先自有源码游戏，至少用两个实际游戏验证共享流程。协议夹具只能证明工程链路。同类型新游戏生产由 Builder 专项承担，与这里复用基础设施。通用自动通关、全引擎接入、多人云平台和无人审批发布仍不列入首轮范围。

## 4. 用户流程与模块分工

用户从“选择游戏与版本 → 提出问题/改进目标 → 确认验收与改动范围 → 查看测试证据 → 审阅候选修改 → 查看回归与前后对照 → 接受或继续迭代”完成任务。只读分析可直接交付报告，不强制创建修改提案。

| 模块 | 负责 | 输出如何被使用 |
|---|---|---|
| Research | 查证外部机制、资料、竞品信息，保留来源与日期 | Designer 形成假设；外部观点不能替代当前游戏实测 |
| Designer | 澄清目标，提出设计假设、改动方案和权衡 | Tester 制定验证；执行器生成待审批差异 |
| Tester | 建立场景、执行测试、复现问题、记录证据 | Finding 与 QA 判定；不负责宣称主观“更好玩” |
| QA | 对照既定验收检查覆盖、退化与证据充分性 | 给出通过/失败/不足和原因，不以角色投票代替事实 |
| Builder / 修改执行能力 | 按授权生成候选差异，在隔离工作区应用和验证 | 已有游戏交付可审查修改；新作按专门设计生成候选，均复用共享 Runtime |
| 共享平台 | 项目接入、身份与范围、版本、执行、证据、审批和追踪 | 所有角色复用同一事实来源 |
| 人类 | 定义产品目标，批准改动，评价体验与接受结果 | 接受不抹去失败证据；合并/发布单独记录 |

不要求每个任务启动所有角色。一次明确的 bug 修复可以只用测试、分析与修改流程；只有复杂任务有必要拆成角色协作。

## 5. 项目与证据的共同语言

文档中有两类“项目”：`docs/projects/` 是 Lab 能力模块的设计目录；用户接入的 Game Project 是被分析的游戏。Designer、Tester、Research 是能力模块，不是用户的三款游戏。

一个游戏可有多个测试目标（逻辑、浏览器、性能等）。当前 targetId 表示执行配置，不能直接当作未来 projectId；本地源码版本也不能当成旧模拟器 GameConfigVersion。后续项目隔离须统一覆盖任务、运行、证据和提案，而不是只加一个项目下拉框。

稳定的追溯链为：游戏与能力 → 被测源码/构建 → 场景与验收 → 执行与原始证据 → Finding/假设 → 修改提案与审批 → 新版本回归 → 人类接受。分析任务可停在证据/报告，修改任务必须保留前后关联。

## 6. 产品验收与衡量

首个可用版本要求：两个真实游戏复用共享流程；用户可在页面完成基线、Finding、修改审批与回归；至少一个实际问题获得可解释修复；不可达目标、拒绝修改和证据不足也能正常结束；第二个目标的接入不需要在共享服务中添加游戏名分支。

从实际使用记录接入耗时、定位首个可复现问题的耗时、人工介入次数、错误通过次数、修改接受率、模型/执行成本和回归耗时。记录样本数与失败，不预设无依据的商业指标。比较同类任务的人工/通用编码助手流程后，再判断平台是否节省时间。

首轮不要用“玩家胜率提升”证明成功，除非策略、样本和实验条件足以支持。主观乐趣与体验仍需目标玩家反馈；自动玩法策略只能提供它所覆盖的视角。

## 7. 当前基础与下一步

共享 Runtime、本地版本证据、Finding 导入和审批后隔离回归已有实现。完整产品仍缺：独立验收程序保护、源码到实际运行产物的构建关联、可移植的真实游戏隔离回归、前后指标对照、简化的任务入口与真实模型效果验收。

下一步先补可信验收和接入，再用真实任务检验模型与产品价值。具体设计见 [可信改进验证](../platform/IMPROVEMENT_VALIDATION_DESIGN.md)，开发排序见 [路线](../design/DEVELOPMENT_ROADMAP.md)。
