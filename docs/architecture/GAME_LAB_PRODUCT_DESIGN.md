# AI Game Lab 产品总设计

层级：Architecture。2026-11-12，按用户对已有游戏改进与同类型游戏制造的要求统一。整体产品定义以本文为入口；实现状态见 [task-state](../state/task-state.md)。

## 1. 两条产品主线

**分析改进已有游戏**：理解机制、发现/复现问题、优化数值或性能、扩展功能，交付证据与可验证改动。

**设计制造同类型新游戏**：从类型、参考机制和创作目标出发，设计本作品的玩法与差异，生成源码、素材组合、可玩构建与验收报告。也支持使用明确可复用的模板或源码派生作品。生产能力属于 Lab 正式目标，不因近期先做测试基础就被删除。

两条线共享研究、设计、执行、版本、测试和审批。新作以规格作为首次验收基准；已有游戏以固定版本与改进目标作为对照。近期以一个受控模板做实生产链，不直接承诺任意类型、任意引擎或无限批量生产。

## 2. 五个模块组成一条交付链

| 模块 | 在已有游戏中 | 在同类型新作中 | 设计入口 |
|---|---|---|---|
| Research | 查证机制、分析竞品与问题 | 研究类型规律、玩家需求、参考机制与差异空间 | [Research](../projects/03_AI_Research_Agent/README.md) |
| Designer | 提出有依据的改进方案 | 产出可实现的 GameSpec、内容/素材需求和验收目标 | [Designer](../projects/01_AI_Game_Designer/README.md) |
| Builder | 受控修复或扩展源码 | 模板实例化、实现玩法、构建、预览与打包 | [Builder](../projects/05_AI_Auto_Game_Developer/README.md) |
| Tester | 复现与前后回归 | 按规格验证核心流程、边界与可玩闭环 | [Tester](../projects/02_AI_Game_Tester/README.md) |
| QA 团队 | 判断改进与退化证据是否充分 | 检查规格覆盖和交付风险，形成质量建议 | [QA](../projects/04_AI_Game_Agent_Team/README.md) |

Research 可按需调用，简单任务不必启动整套团队。Builder 是生产执行职责，设计为现有后端模块；外部编码模型可以通过共享 Gateway 和工具参与，但不是另一个产品 Runtime。

## 3. 同类型生产示例

用户给出“短局俯视角生存游戏”的方向，Designer 明确输入、成长、敌人压力、胜负和重开，并给出两个有规则差异的规格，例如“热量管理换取爆发”与“部署物组成防线”。它们可共享渲染、输入、存档和构建模板，但具有不同核心决策与内容。

Builder 先做一个可玩的完整切片，Tester 检查主循环与边界，用户体验反馈再驱动内容扩展。第二个作品复用同一生产流程，不能通过共享平台里的游戏名特判实现。原型可以使用标注的占位资产；可交付候选需资产来源、正式/占位状态清楚。

不承诺一次生成即达到商业成品质量。生产成熟度分为工程可运行、玩法闭环、规格达标、人类体验接受与发布准备；平台分别保留依据。

## 4. 实施取舍与验证

当前共享执行、本地证据和隔离提案已经提供基础；2026-11-13 已交付 ART-01 规格交接首版与 B-01 可玩模板/CLI 实例化，详见 [可玩模板](../platform/PLAYABLE_TEMPLATE.md)。Builder 的模型生产身份、阶段协调、平台生成 UI 和候选包尚待实现。此前 [已有游戏产品设计](EXISTING_GAME_PRODUCT_DESIGN.md) 是第一条线的专项设计，不能再用其中的范围限制排除第二条线。

先完成独立验收与源码构建关联，同时可准备首个模板、规格和交付元数据；随后接 Builder 执行、Tester 与 QA，最终用两个同类作品验证重复生产。不是先把所有基础设施都做完才产出游戏，也不能为追求产出跳过验证。

价值衡量包括达到可玩切片的时间、需求实现完整度、人工修订、错误通过、成本、接受率与第二次生产节约的工作量。主观玩法质量由人类试玩，自动检查不能替代。

完整衔接见 [共享生产契约](../platform/GAME_PRODUCTION_CONTRACT.md)，当前任务排序见 [开发路线](../design/DEVELOPMENT_ROADMAP.md)。多项目并发、多人云服务和全引擎扩展由实际使用需求触发。
