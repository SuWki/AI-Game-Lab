# AI Game Lab 后续开发路线

更新：2026-11-12。性质：State / Decision 层的跨模块开发计划；事实依据见 [项目评估](../reports/PROJECT_REVIEW_2026-11-11.md) 与 [game-demo 实测报告](../reports/GAME_DEMO_BASELINE_2026-11-12.md)。本文是后续开发建议，不把规划完成等同于代码实现或既有冻结契约已经变更。进度唯一来源仍为 [task-state](../state/task-state.md)。

## 1. 产品目标与默认范围

**最新范围补充：已有游戏改进与同类型新游戏制造都是正式目标。** 总入口为 [产品总设计](../architecture/GAME_LAB_PRODUCT_DESIGN.md)；五模块交接以 [生产契约](../platform/GAME_PRODUCTION_CONTRACT.md) 为准。下文已有游戏优先的阶段历史不再作为排除 Builder 的依据。

### 生产线开发顺序

1. VAL-01/ADAPT-01 建立独立验收与构建来源；同时开展 ART-01 共享产物元数据、Designer D-N1 规格草案与 Builder B-01 首模板。D-N1 的结构化保存依赖 ART-01，首模板可无模型验证，无需等所有技术债清偿。
2. B-02/03 实现版本化交付和新建工作区，B-04/05 接 Builder 身份、工具与有界生产阶段；Tester T-N3 提供新作验收，QA Q-N2 固定候选证据。
3. B-06 交付任务页面、可玩预览和候选包；B-07 用同一模板生产两款有核心规则差异的作品，记录成本与人工修订。首件作品先完成可玩切片，再扩大内容范围。

各模块细分任务与验收集中在其 README 导航，避免把全部任务再复制到本表。新生产尚未实现；已有迭代能力继续维护，不另建执行平台。

**2026-11-12 用户明确：研发主线是 AI Game Lab 平台，demo 仅作为验证样例。** 三批核心代码已交付：共享 Runtime 可靠性、版本化本地测试与 Finding/QA、人工批准后的隔离修改回归，见 [交付报告](../reports/THREE_BATCH_DELIVERY_2026-11-12.md)。下文任务表保留设计与验收清单，不代表全部尚未开发；M1 的真实供应商验收仍待完成，不能以单元测试代替。

当前后续顺序：独立审查并修复 → 冻结独立验收与构建关联 → 可移植真实游戏接入及真实模型验收 → 前后改进对照和工作台。真实模型有凭据时可先做受限只读/测试验收，但自动修改的质量结论依赖独立验收。Research 抓取边界、旧模拟 QA 的证据固定、通用数据库迁移和多项目隔离按技术债单独推进。Builder 按顶部首模板切片计划实施，不直接扩成全引擎无人生产。

方向与职责以 [产品总设计](../architecture/GAME_LAB_PRODUCT_DESIGN.md) 为准；新增实现契约见 [可信改进验证设计](../platform/IMPROVEMENT_VALIDATION_DESIGN.md)。两项关键差距：当前保留检查 ID 不保证测试逻辑未改变，产物哈希不证明其来自当前源码构建。它们应优先于新增 Agent 或展示指标。

已有 Runtime 的真实供应商验收和审查问题穿插推进；没有凭据时仍可完成 VAL-01/ADAPT-01。上述为本轮补充设计，尚未实现。新增数据结构前补迁移与兼容方案，旧结果不重新标为更高证据等级。

产品目标：围绕已有游戏完成分析、测试、优化和功能扩展。第一交付目标是对用户自己的 game-demo 建立“接入版本 → 提出问题 → 运行测试 → 定位原因 → 生成修改差异 → 回归验证”的完整链路。同类型新游戏通过受控模板生产推进，任意类型与无限量内容不作为首轮承诺。

默认单用户 / 本地 / 单项目，复用现有 Java 单体、React、SQLite。先由 Tester 接真实游戏，Designer 消费测试证据提出改进，Research 提供竞品机制与资料，QA 汇总回归结论。代码生成能力用于已有游戏的受控修改和功能扩展。

按接入能力区分范围：自有源码游戏可读取运行状态、注入输入、执行引擎测试并修改源码；第三方成品游戏先支持实际可获取的画面、操作、录像、日志和官方接口。没有源码、Mod 或扩展接口时，不承诺修改游戏内部功能。两者可共享报告与 Finding，但不能承诺相同的可观测性、复现能力或修改能力。

分析任务成功需交付有来源的事实与待验证假设；修改任务需有被测版本、验收契约、实验结果、提案差异、审批和后测结论关联。Run COMPLETED 或当前 VALIDATED 不直接表示产品目标达成。未达标也是有效结论，前提是如实报告并保留证据。

### M1 的推荐设计选择

- **复用唯一 AgentLoop**，把上下文重建提取为窄职责组件；不建第二条 QA/Builder 循环。
- **完整持久化外部对话协议**：只保存可见文本、调用、结果和追踪元数据，不保存隐藏推理。会话裁剪保留 system/目标和完整 assistant-tool 配对，结果过大保存引用及有界摘要。
- **整批先保存、逐项执行**：审批工具挂起时记住批次位置，恢复先补齐对应结果，再处理剩余项。不能把待审批工具当已完成。
- **不承诺任意副作用 exactly-once**：只读调用可重试；受控写操作使用幂等键；崩溃后结果未知的写操作进入待核对状态，禁止自动重放。数据库事务不包住网络调用。
- **状态更新由数据库条件保证**：不能只靠内存取消集合；状态机负责合法迁移，Repository 保证 compare-and-set。只有成功迁移才发终态事件。
- **结束原因与成功判定分开**：建议新增持久化 termination_reason；预算耗尽、截断和无效循环记明确失败/未完成原因，Gate 仅接受有效完成证据。改变旧 COMPLETED 语义时同步契约、消费方和测试，不静默改写历史 Run。
- **先做最小版本化迁移机制**：迁移有版本号、事务、升级测试和备份/恢复流程；具体采用轻量 runner 或既有工具在 RT-00 定稿，不为此引入服务。
- **发布模型适配验证**：模型由配置和 Run 快照决定，先核实账户支持的模型及模式；不在多个服务中硬编码供应商别名。

### M1 验收矩阵

1. HTTP 请求中工具 schema 合法，模拟服务只在收到正确工具定义时返回调用。
2. 模拟服务检查前一轮工具结果中的随机标记，未包含则拒绝推进；防止固定剧本掩盖上下文缺失。
3. 一次返回 3 个工具，中间需审批；批准和拒绝两条路径均无丢失调用、无重复副作用。
4. 在 LLM 返回前、工具落库前后、审批前后注入进程中断，恢复结果可解释；旧库升级后仍可读历史记录。
5. 取消与 LLM stop 并发、重复 resume、重复 approve、未知工具、越权工具均有确定结果。
6. HTTP 延迟、反复 429/5xx、预算耗尽、输出截断、队列满载有明确终态/原因；不会误通过 QA Gate。
7. 非敏感样例执行至少 3 次真实模型流程，保存版本、种子、调用记录和费用；以目标达成/如实未达成评价，记录失败样例。该项是发布前人工可查看的验收，不进入日常每次 CI，也不在本次规划中消耗付费凭据。

## 4. M2：实验与证据

| Task | 交付 | 验收 |
|---|---|---|
| EX-01 指标契约 | 明确胜率、胜率差、DPS 方差、胜场占比、样本占比及单位、缺失值 | 相同数据所有页面/报告解释一致；保留旧字段兼容映射，废弃旧含混名称有版本说明 |
| EX-02 有效平衡判据 | 第一版以 per-build 胜率差和置信区间为主；DPS 仅有真实 per-build 统计后启用 | 小样本/无样本不得 PASS；均匀样本但极端胜率能发现失衡；零胜场不被占比 0 当健康 |
| EX-03 实验提交与恢复 | 提交即有可查询 ID；参数/版本/数量上限在入队前校验；失败可查询 | 无 runId 的手动实验也能看到失败；并发相同幂等键行为确定；服务重启不永久 RUNNING |
| EX-04 配置审批一致性 | 事务内抢占 PENDING + 校验 baseVersion + 生成新版本；关联 tool_call 观察 | 重复批准最多产生一个新版本；过期提案明确冲突；拒绝不产生版本；旧版本保留 |
| EX-05 Gate 证据绑定 | Gate 固定本次评估使用的 experimentId、版本、Finding 集合/引用与判据版本 | 同配置出现新实验不改变既有裁决解释；缺失或不合格证据为 INCONCLUSIVE |
| EX-06 业务验收 | 固定三个代表性任务：可改善、不可达目标、拒绝修改 | 结论引用真实前后实验；不能编造“已达标”；批准和拒绝都可完成业务流程 |

EX-02/05 涉及 Phase 3 已冻结 games-share / latest-DONE 语义，应形成新的决策记录及兼容方案；本计划提出变更方向，现有数据和旧验收结果不重解释。EX-01 设计可与 M1 的非依赖工作交错，但全链路验收必须等 M1 完成。

## 5. M3：能每天使用的工作台

- UX-01：以 Workflow 为入口，任务详情整合 Run、步骤、工具结果、审批、实验和报告；补取消/重试和状态原因，隐藏内部子角色手动创建入口。
- UX-02：补一个精简 QA 详情视图：角色状态、超时、Finding、自动 Gate 原因、证据链接、人工裁决及理由。每项都连到已有证据，避免先做装饰性大屏。
- QA-01：deadline 持久化，重启不重置预算；区分 assignment TIMEOUT 与子 Run 实际状态，界面如实显示；Gate 不把预算退出视作角色成功。
- SAFE-01：启用抓取前限制 http/https、解析 IP 与每跳重定向、内网/回环/元数据地址、下载大小、MIME 和总耗时；测试使用本地受控替身，不真实探测内网。
- OPS-01：开发默认回环监听，开发事件端点仅 dev profile；环境检查验证实际版本及运行配置，错误日志不泄露密钥；增加按锁文件安装的 CI、旧库迁移检查和备份恢复说明。
- TEST-01：清理测试中的未模拟请求与 act 警告；保留真实错误路径断言；UI E2E 覆盖任务创建、运行、审批、取消、失败原因和证据查看。

退出标准：从空环境说明可以启动；用户通过 UI 完成 EX-06 的三类任务；一次服务重启后待审批任务可恢复；没有无说明的永久加载或“已失败但列表仍成功”。

| Task | 实现范围 / 交付 | 退出条件 |
|---|---|---|
| GD-01 复现入口 | 固定 commit、依赖、源码配置哈希、策略版本；把测试中的全局 RNG/时钟替换改成引擎显式注入，保留正常浏览器默认值 | 同一版本/种子/动作序列重复得到相同关键状态；不同种子确实生效；不改血量、不强制结算 |
| GD-02 真引擎适配 | Java GameAdapter 启停一个受控 Node 子进程，调用实际 TS RunEngine；映射 observe/act/tick/events/metrics，固定 tick 含义和超时；另设 Playwright 浏览器测试通道 | 从平台执行一局并查看终态、版本、策略、事件；停止后无孤儿进程；浏览器场景测试与引擎自然对局分开标记 |
| GD-03 首个可复现 Finding | 以本次“已成型却报告未成型”的结算矛盾为首案；生成隔离源码差异，统一成型判断，补失败回归并运行浏览器结算检查 | 原版用例失败，修复版通过；hinted/committed/matured 与胜负组合均核对；报告不能把死亡自动归因于未成型 |
| GD-04 一次改进实验 | 先校准操作策略，再针对 Boss 阶段失败提出一个数值或行为假设；同种子/策略/版本配对比较，每次只改一个因素 | 起步 3 流派 × 2 策略 × 10 种子；保存死亡位置/伤害来源/构筑阶段/Boss 剩余 HP 等；小样本只做探索，不据此宣告平衡 |
| GD-05 一项功能扩展 | 建议增加可导出的单局复盘：节点选择、流派阶段、关键受伤与死亡原因；复用 MetricsTracker，先做事件 JSON 和简洁查看 | 新功能有可运行差异与验证；原有开局、升级、暂停、结算回归通过；数据缺失显示未知，不生成假归因 |

适配器采用两条测试通道：引擎通道负责快速逻辑回归与控制变量实验；浏览器通道负责渲染、输入、UI 流程和实际帧推进。引擎通过不能替代浏览器通过；使用 QA hook 强制进入场景不能计作自然通关。

本 demo 的 `src/data/*.ts` 是运行时权威数据，`public/data/*.json` 是导出产物。提案必须修改实际生效的 TS 源或建立明确的受控覆写入口，重新构建后记录哈希；不能只修改 JSON 就声称游戏已优化。主平台 Java 模拟器的流派与公式也不能替代真实 RunEngine 的结果。

首次接入以独立命令和只读结果导入开始，再映射平台 TestPlan/Finding/Experiment。Node 是游戏执行子进程，不是新增业务服务。保留版本不匹配、依赖缺失、超时、中断和证据缺失的错误分类；单 Run 隔离 RNG、时钟与存档。

源码扩展沿用 Task/Run/Proposal 与共享执行能力。在隔离工作区生成修改，执行相关构建与回归，交付差异和证据；自动模型写操作还需通过 M1 对应验收。不要先重写约九千行的 RunEngine：先抽取 RNG、时钟和测试边界，再按具体修改逐步拆分。

## 8. 开发纪律与近期启动点

每项遵循：读冻结契约 → 更新该项设计 → 写能暴露真实缺口的行为测试 → 小范围实现 → 相关回归 → 全量阶段验收 → 更新 task-state/tech-debt。新行为需要同步 API/事件/前端消费，旧测试不得只改期望值掩盖错误。

下一批为 **VAL-01 + ADAPT-01**，解决测试独立性与实际运行版本的可信性，再以 E2E-01 验证真实用户任务。GD 场景按需要选取；涉及 Schema 与 Gate 语义的变更先补契约和迁移，不以新增文档宣称功能完成。

每阶段验收衡量四件事：业务结论是否有证据、失败能否解释、重试是否重复副作用、人工能否接管。测试数量、Agent 数量与文档页数均不作为完成标准。
