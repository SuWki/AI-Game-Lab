# 已有游戏改进的可信验证设计

层级：Platform。2026-11-12。**待实施设计**：下列新增字段和规则不是现有 API 承诺。当前协议见 [本地执行](LOCAL_GAME_TEST_EXECUTION.md)，用户任务与角色职责见 [产品设计](../architecture/EXISTING_GAME_PRODUCT_DESIGN.md)。

## 1. 现有实现与缺口

| 已实现 | 尚不能证明 |
|---|---|
| 声明源码清单、执行前后哈希、产物哈希 | 运行的产物确实由这一份源码构建；声明范围外的依赖一致 |
| coverageComplete 与唯一检查 ID | 测试覆盖充分、测试逻辑未被修改、断言仍有同样含义 |
| 独立工作区应用修改并保留基线检查 ID | 候选修改没有把测试改成无条件通过 |
| 有版本的 TestPlan/Finding/QA 结果 | 前后实验条件公平、目标指标改善或用户体验变好 |

代码依据：LocalChangeService.create 允许编辑声明范围内文件；get 通过检查 ID 集合判漏测。若测试脚本也在声明范围内，可以被修改后继续返回相同检查 ID。LocalEvidenceService 的产物指纹是身份记录，并未建立构建生产关系。上述是源码可见的设计缺口，本轮没有执行攻击式复现或修改生产实现。

## 2. 冻结验收契约

在候选修改产生前保存验收快照：目标、基线执行、允许改动路径、检查 ID 和语义版本、预期行为、指标单位/方向/阈值、场景/种子/策略版本、必需产物、停止条件与预算。暂先作为已有本地上下文的版本化结构设计，实施时补迁移和兼容测试；不创建平行的任务系统。

划分 editableSources、acceptanceFiles、generatedArtifacts。验收程序与它读取的基准数据由操作者控制并固定哈希，运行器也固定版本；模型可读，但普通改进提案不可写。源码测试可以和产品一起修改，独立验收仍需由冻结的外部检查执行。仅冻结 ID 或仅把文件设只读不足以建立独立性。

确需调整错误测试时，提出单独的“验收变更”，解释差异并人工接受，生成新的契约版本，在旧游戏基线上重跑；此时不能将改变判据后的 PASS 宣称为同一实验的修复。

必备反例：修改测试为恒真、保留 ID 但改变断言、删除场景/改变种子、修改预期数据，均不得让普通候选进入改进通过。新功能允许新增验收，但旧契约检查继续保留。

## 3. 接入、构建与执行身份

未来接入配置区分准备、构建和验证阶段；保持预注册参数数组，不开放模型任意拼接命令。声明工作目录占位符、输入/输出范围、解释器版本、依赖锁文件、所需存档和可用观察/动作能力。第一版无需同时支持所有游戏引擎。

每次隔离验证记录：源码清单、验收版本、执行配置指纹、工具链/依赖信息、构建命令与退出状态、构建输出指纹、实际运行入口与执行 ID。在干净的本次工作区构建，构建失败不得继续借用旧 dist。无法重建的外部成品记录二进制版本与来源，按成品观察范围出结论。

产物按执行保存不可混用的目录及引用。至少保留原始结构化报告、失败日志和必要截图/动作记录；仅有哈希但文件已被覆盖，不算仍可复核的证据。加入大小限额和保留策略：被提案或验收引用的证据不能被静默清理，缺失时明示证据不可用。

验收反例：源码变了但运行旧构建；两个任务共享输出；产物路径存在却来自前次执行；相同源码但验收版本改变。必须能拒绝或分别标识，不合并为同一实验。

## 4. 前后实验与结论

修 bug：固定复现失败，候选版本通过独立检查，必要旧功能回归不退化。

调数值/性能：预先确定测量环境、策略、场景与种子集合，基线与候选配对执行，输出每组原始结果、效应大小、样本数与不确定性。预算不足时停止并保留探索性结论；不选择性删除失败运行，不把命令执行次数当成玩家样本。性能测试控制构建模式、设备和预热条件；无法控制则标明不可直接比较。

扩功能：新需求的正常/异常/边界场景与旧回归同时验收。主观体验建议单独展示，交由人类评估，不由自动指标替代。

使用三层结果：执行状态（现有状态机）、检查判定（现有 PASS/FAIL/INCONCLUSIVE）、目标结论（待实施：达到/未达到/证据不足/需主观评价）。现有 VALIDATED 只表示当前注册检查满足协议，不能升级为游戏优化已达标。

结论固定引用基线/候选执行、验收版本、指标结果与理由；后续运行不能静默改变旧结论。保持与旧模拟 ReleaseGate 分开，只有明确指标映射后才加入统一展示。

## 5. 提案、批准与接受

审批对象固定为基线、允许修改范围、差异、验收契约与执行预算。批准后任何差异或验收变动都需新提案；基线变化要求重新建立对照。验证失败保存失败产物并重新提案，禁止自动无限迭代。

隔离验证通过后仍需单独的接受记录：选择是否采纳、理由、对应提案和回归证据。未来合并步骤先检查目标目录基线，再应用/合并并重跑必要检查；不因工作区验证通过而直接覆盖用户修改。当前仍交付人工合并的工作区，不新增自动合并接口。

## 6. 实施顺序与兼容

1. 验收清单与路径权限、冻结独立验证程序，先覆盖恒真脚本与验收漂移反例。
2. 可移植准备/构建/验证阶段，建立源码到产物的关联及证据留存。
3. 对照实验与目标结论、接受记录，复用现有 Task/TestPlan/Finding/Proposal。
4. 工作台展示完整追溯链并运行真实模型验收。

旧结果保留原始判定并标记其证据级别，不补造验收快照，不将旧 VALIDATED 批量重解释为新标准通过。新增元数据/表之前提供迁移、旧库可读和回退说明；接口字段版本化，缺元数据返回“证据不足”或只展示原协议结论。

这些规则面向可信本地目录中的实验可靠性。运行恶意项目所需的 OS 沙箱、远程授权和多实例隔离是独立工程，不能用文件清单替代。
