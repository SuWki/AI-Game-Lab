# Designer 产品定义

Designer 将游戏目标转为可实施、可验证的设计方案，服务已有游戏分析改进与同类型新游戏创作。当前 ORBITAL 数值模拟是已实现的实验场景，不是全平台类型限制。

## 输入与交付

已有游戏输入版本、问题、证据和改动范围，输出假设、改进提案与前后验证要求；新游戏输入类型、玩家、平台、时长、参考与预算，输出原创 GameSpec、差异化选择、内容范围和验收需求。没有现成游戏配置时也可先完成新作设计。

GameSpec 至少覆盖核心循环、状态与输入、胜负和重开、成长/资源规则、界面反馈、素材需求、需求编号与验收项。每条设计注明依据或假设。输出可读文档与可交接结构，交由 Builder 实现、Tester 验证、QA 评审。

## 决策原则

改动需要说明问题、证据、方案、预期与验证；简单明确改动直接给方案，有重要取舍才比较多个候选。模拟指标只能解释模拟环境，不能直接推断真实游戏平衡。方案完成、模型正常结束、测试通过和玩家体验改善分别报告。

参考研究帮助识别机制与设计空间，成品有自己的主题、规则/成长差异和内容。体验目标保留人工评审项，不把主观感受转成虚构概率。用户批准范围内推进，需求冲突或范围变化明确呈现。

## 范围与当前状态

现有配置、实验、文档、研究消费和审批基础已实现；结构化 GameSpec、需求到代码/测试追踪与新作生产交接待开发。Designer 不承担独立测试裁决、自动审批自己的修改或公开发布。

技术基础见 [技术设计](技术设计.md)，当前扩展、工具/Prompt、任务及验收见 [演进设计](演进设计.md)。不再将“固定跑 10000 局”和“三种 Build”作为所有任务要求。
