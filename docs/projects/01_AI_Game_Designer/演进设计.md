# Designer：真实游戏改进与新作设计

层级：Project。2026-11-12。现有 P0–P8 是 ORBITAL 配置/模拟设计基础；以下新增契约为待实施。共享交付结构引用 [生产契约](../../platform/GAME_PRODUCTION_CONTRACT.md)，运行机制引用 [Runtime](../../platform/AGENT_RUNTIME_RECOVERY.md)。

## 产品与技术边界

Designer 产出可被实现和检验的 GameSpec，或已有游戏的有证据改进提案。类型特有的武器/Build/波次只是示例，不能作为所有项目的必填字段。新建、派生和优化使用显式任务模式：已有版本用于修改；新建使用创作简报与参考研究，不能强行要求 v001。

当前模拟工具只适用于其 GameConfig 和模拟语义；真实本地任务由 RuntimeConversation 换为受限本地工具，不能把 Java 模拟结果当成 Phaser/Unity 实测。当前 create_design_document 保存文本，不具备 GameSpec schema 校验和版本化交接。

## Agent 与 Prompt

输入：简报/当前规格版本、事实证据、能力清单、预算与排除项。步骤：核对约束 → 分解体验目标 → 选择方案 → 写清规则与状态 → 给需求 ID 和可观察验收 → 交付。简单明确改动不强制生成三套方案；有重大取舍时提供有限备选和推荐理由。

规则规格至少覆盖：核心循环，玩家输入，胜负/进度，数值单位与边界，异常/暂停/重开，内容结构，界面反馈，素材需求。每项验收绑定需求 ID；“更好玩”“有高级感”等目标转成可讨论的体验假设与人工评审项，不能伪造成确定数值门槛。

停止：规格足够进入切片、证据不足、需求冲突、预算耗尽或人类拒绝。输出同时给事实、假设、决策和未知项。长期 Prompt 用新版本资源记录，冻结实际选中内容/hash，不能仅修改未启用的种子文件就宣称角色已采用新行为。

## 工具与衔接

当前工具以 DefaultAgentTypeResolver 与 RuntimeConversation 的执行快照为准：模拟 Designer 的 10 项工具含研究读取；本地 Designer 仅结果/源码读取与提案。两组不是叠加的无限权限。

待新增的业务能力为 GameSpec 校验、保存版本与提交交接；实现时通过现有 ToolRegistry 注册，输入为生产契约 envelope，输出 artifactId/revision/hash 与结构校验错误。仅写设计产物不修改游戏；需要写游戏时生成审批提案。Designer 不批准自己的提案，也不更改冻结验收程序。

Research 输出的机制观察进入候选设计理由；Builder 收到规格版本和实现范围；Tester 接收需求到验收的映射。Builder 提出不可实现约束后生成新规格版本，不在代码中暗中删需求。

## 任务与验收

| 任务 | 依赖/范围 | 验收 |
|---|---|---|
| D-N1 规格契约 | ART-01；设计文档服务，规格草案可先行 | 新作/优化两种输入可校验；缺胜负或重开返回具体缺项 |
| D-N2 研究到方案 | Research 来源与规格版本 | 设计引用研究 revision；证据与假设分栏；单一来源不自动成事实 |
| D-N3 交给制造 | Builder 计划、Tester 验收 | 同一规格的需求 ID 可追溯到实现与测试；规格更新令旧候选需复核 |

挑战验收：指定非战斗类游戏仍能设计；没有可用实测时不报平衡达标；不可能的范围给缩减方案；两款同类新作有实质机制差异。性能和模型效果通过固定任务记录时长、成本与人工修订，不承诺固定 10000 局或特定机器速度。
