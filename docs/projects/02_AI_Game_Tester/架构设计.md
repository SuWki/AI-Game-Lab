## 1. 产品目标

让 AI 能够以受控、可复现、可追踪的方式参与游戏测试全流程：

```text
Game Build(= ConfigVersion)
    ↓
Test Plan（测试计划）
    ↓
AI Tester（Agent Run，经统一 Agent Runtime 执行）
    ↓
Test Run（run/step/tool_call 全程落库）
    ↓
Observation（getState / collectEvents / getMetrics）
    ↓
Analysis（Invariant 检查 + LLM 判断）
    ↓
Finding / Issue（severity + 复现步骤 + 证据）
    ↓
Test Report（Markdown Artifact）
    ↓
写回 Project（其他 Agent 可消费）
```

它不是聊天机器人，不是"跑一局截个图"。核心判据：

1. **闭环**：Plan → Execute → Observe → Analyze → Decide → Report，全部通过 Tool 与游戏环境交互。
2. **可复现**：同一 seed + 同一 Test Plan + 同一 Action Sequence ⇒ 相同的 Observation / Event / Metrics。
3. **可追踪**：每一步观察与判断都能从 Run Trace 还原（工作流 §32）。
4. **可协作**：测试结果以结构化 Finding 落库，Designer / Builder 未来可直接消费。

## 2. 第一阶段边界（重要）

第一阶段 **不做**：

- 启动 Steam / Windows 真实游戏、鼠标键盘自动化、屏幕读取
- OCR / Computer Vision / 截图分析
- Unity / Unreal Plugin
- Designer ↔ Tester 自动闭环（只冻结数据契约）

第一阶段 **做**：

- 可模拟的确定性 Fake Game Environment（`FakeGameAdapter`）
- 基于 Agent Runtime 的完整测试循环（FakeLlmGateway 可全链路驱动）
- Smoke / Functional / Regression / Boundary / StateTransition 的最小实现
- Invariant 引擎与 Finding 生成
- 测试报告生成（Markdown Artifact）

## 3. 用户使用流程（MVP）

1. 用户在中台创建 **Test Request**（复用 `task` 表，goal 如"验证玩家死亡→结算→返回大厅流程"）。
2. Agent 生成/确认 **Test Plan**（场景列表 + 每场景的 Action 大纲 + Invariants + seed）。
3. 用户点击"执行测试" → 后端创建 Run（复用 `run` 表），AgentLoop 驱动。
4. Agent 通过工具操作 Fake 游戏环境：`game_start / game_action / game_observe / game_collect_events / ...`
5. 发现异常 → 调用 `finding_report` 落一条结构化 Finding。
6. 结束 → 调用 `test_report_create` 产出 Markdown 报告 → Run COMPLETED。
7. 中台查看：Run Trace（复用现有页）、Finding 列表（新页）、报告详情。

## 4. Agent 生命周期

完全复用平台 7 态 Run 状态机（蓝图 §9.2），不新增状态：

```text
PENDING → RUNNING → (WAITING_APPROVAL 仅当触发需审批工具) → COMPLETED / FAILED / CANCELLED / TIMEOUT
```

Tester 特有语义映射：

| 平台状态 | Tester 语义 |
|---|---|
| RUNNING | 正在执行某个测试场景的 Observe→Act 循环 |
| WAITING_APPROVAL | MVP 中基本不出现（Tester 工具均不需审批；预留：未来 stop_game 于真机环境需审批） |
| COMPLETED | 所有计划场景已执行且报告已生成 |
| FAILED | 游戏环境崩溃且无法恢复 / 关键工具失败 |

Agent 内部逻辑阶段（非运行时状态，体现在 Prompt 与 Step 内容中）：

```text
PLAN → SETUP → SCENARIO_LOOP(Observe → CheckInvariants → Act → Advance) → ANALYZE → REPORT
```

## 5. 与 AI Game Designer 的协作（MVP 只定契约）

数据流向：

```text
Designer                          Tester
────────                          ──────
ConfigVersion vNNN ──────────→   TestPlan.configVersion（被测对象）
                                  ↓ 执行
Experiment(数值实验, 共享表) ←──   Balance Observation 类测试直接产 Experiment 行
Finding(新表) ───────────────→    Designer 未来读取 Finding 分析
design_document(测试报告) ──→     人类 / 其他 Agent 阅读
agent_event(TEST_*) ────────→     中台实时可见
```

**契约 1：被测对象是 ConfigVersion。** 每个 TestPlan 必须记录 `config_version`，使"回归测试"= 同一 TestPlan 对新版本再执行一次并对比 Finding 集合。

**契约 2：统计型结论走 Experiment。** 凡是可以表达为"同参数批量模拟 + 聚合指标"的测试（如暴击率实测 34.8% vs 配置 35%），Tester 直接调用共享 `simulate_game` 能力产生 Experiment 行——与 Designer 看到的是同一份数据、同一个幂等键 `(configVersion, seed, count, scenario)`。

**契约 3：缺陷型结论走 Finding。** 结构化字段见技术设计 §7。

MVP 不实现任何一方自动调用另一方；协作通过中台人工流转。

## 6. 核心问题的回答：复用什么，新增什么

> 详细逐项对照表在技术设计 §2。一句话结论：
>
> **复用**：AgentRuntime(AgentLoop/ToolExecutor/状态机/BudgetGuard/LoopDetector)、LlmGateway(+Fake)、ToolRegistry(GameTool SPI)、task/run/step/tool_call/experiment/agent_event/prompt_version/design_document 全部现有表、SSE 链路、ApiResp/ErrorCodes、SQLite。
>
> **新增（Java 模块，零新依赖）**：`gameenv` 包（GameAdapter SPI + FakeGameEnvironment）、`tester` 包（Tester Tools ×8、TestPlanService、FindingService、InvariantEngine、Tester Prompt）。
>
> **新增数据库表（需独立 DB Task 人工批准）**：仅 2 张 —— `test_plan` 与 `finding`。理由：二者是被 Designer/Builder 消费的一等实体，塞进 JSON 列将无法查询/回归对比/状态流转；其余一切（观测、事件、证据、报告）全部复用现有表。

## 8. 成功指标（承接需求文档 §10）

MVP 验收以"过程正确性"为主：

1. FakeLlmGateway + FakeGameEnvironment 全链路集成测试跑通 Plan→Act→Observe→Finding→Report。
2. 同 seed 同动作序列两次执行，Observation 序列逐字段一致。
3. 注入式 Bug（FakeEnv 可编程故障）100% 被 Invariant 或 LLM 分析捕获为 Finding。
4. 无注入 Bug 的健康构建跑出的 Finding 数 = 0（无误报基线）。
5. 全部行为可在 Run Trace 与 agent_event 中还原。

产品层指标（二期起）：Bug 数、Critical/High 分布、复现率、Action/State 覆盖率。

## 9. 架构一致性声明

- 单仓库单后端：Tester 是 `backend` 内的业务模块包，不是新服务。
- 不新建 Runtime/Gateway/Registry/EventBus/数据库连接。
- 不引入任何第三方依赖（FakeEnv 用已有 Jackson + JDK SplittableRandom）。
- 新增表遵循"先提案后实施"，见技术设计 §6 与任务树 T-DB1。
