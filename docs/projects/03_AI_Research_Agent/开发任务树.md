## Phase Goal（R0 最终必须达到的用户可验证能力）

**用户可以通过 API 创建一个 `constraints_json = {"agent_type":"RESEARCH"}` 的 Task，启动 Run 后：**

1. Agent 收到 Research 专用 System Prompt（非 Designer/Tester Prompt）
2. Agent 可以调用 Research 专用 Tools（web_search、fetch_page 等）
3. Agent 不能看到 Designer/Tester 的私有工具
4. Agent 的研究产出（Sources、Claims、Reports）持久化到数据库
5. 研究产出可通过 API 查询、通过 SSE 观测
6. 同一 Task 创建的不同 AgentType Run 互不干扰

**不属于 R0 范围：**
- 前端 Research 页面（后续 Sprint）
- 多 Agent 协作（Research + Designer 联动）
- python_analysis 工具（需要 Python 运行时，后续 Sprint）
- 真实 Web Search API 接入（R0 使用 Stub/Fake，后续 Sprint 接入真实 API）

## 架构歧义与人工决策点

### 歧义 A：DESIGNER 白名单溢出问题

**问题描述：**
当前 `DefaultAgentTypeResolver.toolWhitelist(DESIGNER)` 返回 `null`（表示使用全部已注册工具）。当 Research Tools 注册到 ToolRegistry 后，Designer Agent 会看到并可以调用 Research 工具（web_search、fetch_page 等），这不符合架构设计中 Agent 能力隔离的原则。

**方案 1：将 DESIGNER 改为显式白名单**（推荐）

```java
case DESIGNER -> DESIGNER_TOOL_NAMES;  // 8 个 Designer 工具
case RESEARCH -> RESEARCH_TOOL_NAMES;  // 7 个 Research 工具
```

- 优点：严格隔离，符合 `01_Agent_平台架构.md` §6 的 Agent Tool Set 设计
- 缺点：每次新增 Designer 工具需同步更新白名单
- 对冻结契约的影响：修改 `DefaultAgentTypeResolver`，不影响 AgentLoop 主循环
- 实现风险：低

**方案 2：保持 DESIGNER 为 null，接受工具可见**

- 优点：零改动
- 缺点：违反架构设计，Designer 可能误用 Research 工具
- 对冻结契约的影响：无
- 实现风险：中（行为不正确）

**需要人工决策。**

### 歧义 B：web_search 的 Stub vs 真实实现

**问题描述：**
`04_AIResearchAgent.md` §6 列出 `web_search` 工具，但当前项目无 Web Search API 集成。

**方案 1：R0 使用 Stub 实现**（推荐）

- web_search 返回预设的搜索结果列表
- 后续 Sprint 接入真实 Search API（如 SerpAPI、Bing API）
- 优点：R0 范围可控，不引入外部 API 依赖
- 缺点：E2E 测试只能验证流程，不能验证真实搜索

**方案 2：R0 直接接入真实 Search API**

- 需要 API Key 配置、限流、错误处理
- 优点：功能完整
- 缺点：扩大 R0 范围，引入外部依赖

**需要人工决策。**

### 歧义 C：python_analysis 工具

**问题描述：**
`04_AIResearchAgent.md` §6 列出 `python_analysis` 工具，但当前项目无 Python 运行时集成。

**建议：R0 不实现 python_analysis。** 理由：
1. 需要嵌入 Python 运行时（Jython/GraalPython/进程调用），架构复杂度高
2. Research Agent 的核心能力（搜索→收集→提取→验证→报告）不依赖 Python
3. 后续 Sprint 可作为独立 Task 实现

**需要人工确认。**

### 歧义 D：Research 数据是否需要独立的 status 流转

**问题描述：**
`research_claim` 的 `status` 字段（DRAFT/VALIDATED/DISPUTED）是否需要像 TestPlan 那样有状态机？

**建议：R0 使用简单状态（DRAFT/VALIDATED/DISPUTED），不实现状态机。** 理由：
1. Research Claim 的状态流转由 LLM 在 Agent Loop 中驱动，不需要服务端强制校验
2. 与 Finding 的 OPEN/CONFIRMED/DISMISSED/FIXED 模式一致（Finding 也没有状态机）

**无需人工决策。**
