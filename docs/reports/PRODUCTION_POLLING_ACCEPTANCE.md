# 生产列表轮询验收

对比基线为 `4fdf905`。两个版本各启动隔离的 Java 后端，使用相同 GameSpec、本地模型夹具和审批流程。每个数据库用 SQLite 的 `AFTER INSERT`、`AFTER UPDATE` 和 `AFTER DELETE` 触发器统计业务表受影响的行数，包含原值不变的 UPDATE。每组从状态稳定时开始计数，实际请求 `GET /api/productions` 20 次。测试数据库中只有一条生产记录，构建和独立验收都已登记。

| 状态 | 基线 | 优化后 |
| --- | ---: | ---: |
| 待审批 | 40 | 0 |
| 待审批，重启后 | 40 | 0 |
| 回归通过，待人工评审 | 40 | 0 |
| 待人工评审，重启后 | 40 | 0 |

基线的 160 次写入均为 `production_job` 更新。旧接口每次分别回写构建和验收结果。新版合并两份执行摘要，有变化时保存一行，提案阶段和预算仍从当前记录计算。集成测试清除一项已保存的验收结论，首次轮询补回它，连续 20 次轮询总共只更新该生产一行。

审批前第一次重启保留 `WAITING_APPROVAL` 和提案 ID，模型夹具请求数仍为 4。批准后创建一条回归执行，提案进入 `VALIDATED`，原 Builder Run 收到关联该回归执行的审批结果，再发出第 5 次模型请求并完成。数据库记录 1 条 `RUN_RESUMED` 和 1 次该工具回执更新。第二次重启后，列表继续显示 `REVIEW`，请求数仍为 5。

回归完成时，列表轮询和执行器回调可能同时读取已结束的执行。提案通过 `WHERE status='VALIDATING'` 只提交一次终态，竞争方使用数据库中的结果继续处理审批回执。批准到恢复完成期间，提案表从 4 次更新降至 3 次，对应进入应用、关联回归和保存终态。此次测量针对写入行数，列表仍会读取关联执行、提案和预算。
