## 已确认发现（按需要修复的缺陷列出）

### F1 / P2：重新校验失败后仍宣称候选可交付

位置：`frontend/src/pages/CandidateReviewPanel.tsx:25`、`:31`、`:35`。

React Query 在 refetch 失败时保留上次 data。组件虽然显示 query.error 并禁用表单，但门禁文字只读取旧的 `view.gate.eligibleForDelivery`，没有考虑验证失败。先读取 ACCEPTED/eligible=true，再令 review 返回 409 “Fixed candidate archive changed”，点击“重新载入最新评审”，页面同时显示归档损坏错误和“门禁查询：此版本可交付”。网络断开或后端故障也存在同类旧值风险。

本轮用真实前端和 Edge、确定性 HTTP 夹具复现并截图。该结论是界面缺陷，不声称服务端允许损坏包下载或重新接受。修复应保留历史意见，但把当前交付状态降为“验证失败/未知”，仅最新成功验证才能恢复可交付；同时清理容易混淆的旧成功消息。补充“成功后 refetch 409/网络错误”的回归。

### F2 / P2：生产取消后，评审门禁缓存不随生产状态失效

位置：`frontend/src/pages/ProductionsPage.tsx:17`；`frontend/src/pages/CandidateReviewPanel.tsx:9`；`frontend/src/pages/ProductionCandidatePanel.tsx` 传递评审组件处。

cancel 只失效 production-jobs 查询，候选评审以 candidate.id 独立缓存，组件没有消费生产阶段或当前验收执行的变化。已接受候选点击“取消生产”，同一页面顶部更新为 CANCELLED，底部仍显示“此版本可交付”。复现中 review 请求次数在取消前后均为 1，说明没有重新验证。这不只是另一个标签页并发的延迟，同页面自身操作就能触发。

修复应在取消、候选切换、未决修改等影响门禁的变化后失效相关评审查询，并让已知不满足条件的生产阶段立即阻止可交付展示。刷新生产记录也应同步相关门禁。补充跨组件流程测试，不能只单独 mock CandidateReviewPanel 的最终状态。

复现证据：[机器记录](evidence/sol-independent-review-2026-11-17/ui-reproduction.json)、[取消后仍可交付](evidence/sol-independent-review-2026-11-17/cancelled-but-deliverable.png)、[校验错误后仍可交付](evidence/sol-independent-review-2026-11-17/integrity-error-but-deliverable.png)。本次使用真实组件搭配模拟 API 响应，未重新声称完成真实后端端到端验收。

## 对 Sol 测试与自验收的评价

核对了本地 Surefire XML：760 tests、0 failures、0 errors、0 skipped；Vitest 日志记录 82 项通过。Sol 的报告还记录 Node 12 项和构建通过。本轮没有重新运行整套回归，这些数字属于前一轮实际执行记录；为避免加重用户机器负载，本轮只进行了定向浏览器复现和代码/证据核对。

新建隔离数据库、版本绑定、两个页面冲突、归档篡改和重启字节比较，是有价值的验证。对重开热量差异记录 FAIL，而不是静默标 PASS，也正确。正向夹具排除热量语义且事先声明，只能说明其三个选定标准与评审流程通过，不能说明之前那份完整规格或游戏质量已通过。

“12 个页面能加载”仅为加载烟测；不能证明 Designer、Research、QA、Builder 的真实模型业务闭环全部通过。Sol 的自验收报告总体注明了边界，但“本轮模块可直接继续下一模块”的结论漏掉 F1/F2：其现有测试验证了服务端 false，没有核对同一页面在生产状态改变和请求失败后是否撤回旧 true。

## 修复与再验收顺序

1. 修复 F1/F2，增加失败后缓存和跨组件取消/候选切换测试；在真实页面看到状态一致，再关闭本轮评审模块验收。
2. 对重开热量需求做明确裁决并以新候选修复/复验，保持旧拒绝记录，不静默改写旧包。
3. 补齐规格创建、编辑、保存与接受入口，把 Designer 产物接入 Builder，减少当前依赖手工 API 脚本的步骤。
4. 接入浏览器级规格证据，再按 B-07 用同模板、不同核心规则的两件作品和真实供应商执行完整流程，记录失败、人工介入与成本。
