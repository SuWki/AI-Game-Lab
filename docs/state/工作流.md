# AGL AI 协作开发工作流 v2（AI Autonomous Development Workflow）

> **版本**：v2.0
> **变更**：从"单 Task → 人工验收 → 下一个 Task"模式升级为"自主连续执行 + Sprint Checkpoint 人工验收"模式。
> **兼容性**：v1 全部有效规则全文保留并整合进第二部分（§15 起），旧规则继续有效，但普通 Task 默认自动推进。
>
> **文档结构**：
> 第一部分（§0–§14）：v2 新增的自主执行核心机制。
> 第二部分（§15 起）：v1 有效规则的完整保留与整合。

# 第一部分：v2 自主执行核心机制

## 0. 文档目的

本文档定义 AI Game Lab（以下简称 AGL）项目的 AI 协作开发流程。

项目采用：

AI 主开发 + 人类产品决策 + AI/人类共同验收

的开发模式。

核心原则：

人类负责：
目标、方向、优先级、设计决策、Checkpoint 验收

AI 负责：
架构实现、编码、测试、调试、文档、重复性工作、Sprint 内自主推进

共同负责：
问题分析、技术决策、风险识别、质量保证

---

## 1. 最高优先级行为原则

整个工作流的最高执行原则：

**默认自主推进，遇到 Blocker 才停止，Sprint Checkpoint 才等待人工验收。**

具体要求：

不要把"等待人工验收"作为普通 Task 的默认行为。
不要因为"Task 完成"就自动停止。
不要因为"发现普通错误"就询问用户。

应该优先：分析 → 修复 → 测试 → 再修复。

只有真正需要人做决策时才停止。

本原则优先级高于本文档其他所有关于停止/等待的描述；凡与其他章节冲突，以本章为准。

---

## 2. 默认模式：自主连续执行

### 2.1 自动进入下一个 Task 的前置条件

Task 完成后，只要同时满足以下全部条件，AI 应自动进入下一个 Task，不等待人工确认：

1. 验收标准全部通过
2. 自动测试通过
3. Scope Check 通过
4. 不存在架构/产品决策冲突
5. 下一个 Task 的前置条件已经满足

人工验收从"每 Task 一次"改为"Checkpoint 一次"。

### 2.2 自主权力的边界

AI 的自主权限只限于已经冻结的设计、任务树和工作流范围内。

AI 可以自主解决实现细节问题，但不能自主改变：

- 产品目标
- 核心架构
- 已冻结 API Contract
- 数据模型
- Task Dependency Graph
- MVP 边界
- 已确认的设计决策

遇到需要人做产品/架构决策的问题，必须 STOP，不得猜测。

### 2.3 状态可恢复原则

所有自主推进必须留下可恢复的状态记录（见 §6）。

## 3. Sprint 与 Task 结构

### 3.1 定义

| 概念 | 定义 |
|---|---|
| Task | 最小开发单元 |
| Sprint | 一组具有明确共同目标、可以连续自主执行的 Task |
| Checkpoint | Sprint 结束后的人工验收闸门 |

### 3.2 标准流程

```text
Sprint Start
→ Task A
→ SELF_CHECK
→ AUTO_ACCEPT
→ Task B
→ SELF_CHECK
→ AUTO_ACCEPT
→ ...
→ Sprint Complete
→ CHECKPOINT
→ WAITING_ACCEPTANCE
```

### 3.3 提前退出 Sprint 的条件

只有以下情况可以提前退出 Sprint（进入 BLOCKED）：

- BLOCKED
- 安全/数据完整性高风险
- 架构冲突
- 产品决策冲突
- 连续自动修复失败
- 依赖条件无法满足

除以上情况外，不得在 Sprint 中途停下等待人工。

## 4. Task 生命周期（v2 重定义）

### 4.1 主生命周期（自主推进路径）

保留原有状态，并增加自主推进状态：

```text
PLANNED
   ↓
READY
   ↓
IMPLEMENTING
   ↓
SELF_CHECK
   ↓
AUTO_ACCEPT
   ↓
NEXT_TASK
```

### 4.2 失败路径：自动修复循环

```text
SELF_CHECK
   ↓
FIXING
   ↓
SELF_CHECK
```

最多自动修复 3 个循环（详见 §7）。

### 4.3 连续修复失败路径

```text
FIXING
   ↓
BLOCKED
```

### 4.4 人工介入路径

```text
BLOCKED
   ↓
WAITING_HUMAN_DECISION
   ↓
FIXING / IMPLEMENTING
```

### 4.5 Sprint 完成路径

```text
AUTO_ACCEPT
   ↓
SPRINT_COMPLETE
   ↓
CHECKPOINT
```

### 4.6 人工验收通过路径

```text
CHECKPOINT
   ↓
SPRINT_APPROVED
   ↓
NEXT_SPRINT
```

### 4.7 WAITING_ACCEPTANCE 的新定位

"WAITING_ACCEPTANCE"不再作为每个普通 Task 的默认状态。

它只用于：

- Sprint Checkpoint
- 明确要求人工验收的特殊 Task

v1 中 `WAITING_ACCEPTANCE → FIXING → SELF_CHECK → WAITING_ACCEPTANCE` 的验收驳回循环仍然有效，但只发生在 Checkpoint 层面：

```text
WAITING_ACCEPTANCE → FIXING → SELF_CHECK → WAITING_ACCEPTANCE（仅限 Checkpoint / 特殊 Task）
```

v1 中 `IMPLEMENTING → BLOCKED → WAITING_DECISION` 仍然有效；`WAITING_DECISION` 与 v2 的 `WAITING_HUMAN_DECISION` 同义，两者等价使用。

## 5. Autonomy Boundary（AI 自主决策权限）

### 5.1 AI 可以自主处理

以下情况 AI 应当自行分析、修复、验证，不打断用户：

- 编译错误
- 单元测试失败
- 集成测试失败
- 普通运行时异常
- 明确的代码实现细节
- 重构局部实现但不改变公开契约
- 测试补充
- 文档格式修正
- 明确的依赖安装/环境问题
- Maven/构建重试
- 临时测试数据问题
- 明确由已有规范决定的文档冲突

### 5.2 AI 不得自主决定

以下任何一条出现时，必须立即进入 BLOCKED：

- 修改产品需求
- 修改 MVP
- 修改核心架构
- 修改数据库核心模型
- 修改 API Contract
- 修改 Agent Runtime 状态机语义
- 删除已有验收标准
- 绕过测试
- 降低测试标准
- 修改 Task Dependency Graph
- 引入重大第三方依赖
- 修改安全策略
- 接受数据丢失风险
- 接受事务一致性风险

## 6. Progress State / 断点恢复机制

### 6.1 状态文件

文件：`docs/state/task-state.md`

该文件作为 AI Autonomous Development 的持久化进度状态。

### 6.2 每个 Task 开始时更新

- Current Sprint
- Current Task
- Status
- Start Time
- Completed Tasks
- Current Step
- Modified Files
- Test Status
- Blockers
- Next Action

### 6.3 每完成一个 Task

- 标记 Task DONE/AUTO_ACCEPT
- 记录测试结果
- 记录修改文件
- 更新 Completed Tasks
- 写入 Next Action

### 6.4 进入 BLOCKED 时必须记录

- Blocker
- 已尝试方案
- 为什么无法自主解决
- 需要人工决定的问题
- 候选方案
- 当前推荐方案
- 等待的具体决策

### 6.5 断点恢复协议

这样即使发生 DeepSeek 上下文中断、IDE 重启、API 超时、会话结束，下一次启动时只需要读取以下四个文件即可恢复全部上下文：

1. `docs/state/工作流.md`（本文件）
2. `docs/state/task-state.md`
3. `docs/projects/01_AI_Game_Designer/技术设计.md`
4. `docs/projects/01_AI_Game_Designer/开发任务树.md`

### 6.6 task-state.md 读写规则

| 时机 | 动作 |
|---|---|
| Task 开始 | 覆盖更新 Current Task 区块（§6.2 字段） |
| 自动修复每轮结束 | 更新 Current Step / Test Status / Fix Loop Count |
| Task 完成 | 追加到 Completed Tasks，写 Next Action |
| 进入 BLOCKED | 写入完整 Blocker 报告（§6.4 字段） |
| Checkpoint 验收通过 | 更新 Sprint 状态为 SPRINT_APPROVED，归档已完成 Sprint 的临时状态 |

task-state.md 是唯一进度事实来源（Single Source of Truth）。它与 Git Commit 记录互补，不互相替代。

## 7. 自动修复循环

普通失败不得立即停止。

标准循环：

```text
Task
→ Test
→ Fail
→ Diagnose
→ Fix
→ Test
```

最多自动修复 3 个循环。

如果 3 次后仍失败：进入 BLOCKED。

### 7.1 立即停止例外清单

以下情况不进入自动修复，立即停止并进入 BLOCKED：

- 数据损坏
- 数据丢失
- 事务一致性问题
- 安全漏洞
- 并发一致性风险
- 架构冲突
- API Contract 冲突
- 产品需求冲突

---

## 8. Sprint 启动规则

AI 收到：

"开始执行 P1 Sprint"

后，必须按顺序：

1. 读取工作流（本文件）
2. 读取技术设计
3. 读取任务树
4. 读取 task-state.md
5. 判断当前 Sprint 的第一个未完成 Task
6. 检查依赖
7. 自动开始执行
8. 完成后自动进入下一个 Task

不得因为单个 Task 完成就停止等待人工。

---

## 9. Sprint Checkpoint

### 9.1 Checkpoint 设置位置

Checkpoint 必须设置在以下节点完成时：

- P0 基础设施完成
- Agent Runtime 完成
- LLM Gateway 完成
- Tool Registry 完成
- Simulation/Experiment 核心完成
- Config/Approval 完成
- Frontend 完成
- E2E 完成

### 9.2 Checkpoint 行为

到达 Checkpoint 后：

1. 停止自主开发
2. 输出完整阶段报告（见 §13.2，素材结构见 §21）
3. 等待人工验收

人工验收使用 §38 的人工验收固定指令与 §39 验收等级（PASS / CONDITIONAL PASS / FAIL）。

验收通过：`CHECKPOINT → SPRINT_APPROVED → NEXT_SPRINT`。
验收 FAIL：`WAITING_ACCEPTANCE → FIXING → SELF_CHECK → WAITING_ACCEPTANCE`。

---

## 10. 实时进度规则

如果单个操作预计超过 10 秒，必须阶段性播报：

```text
[阶段 1/5] 分析依赖
[阶段 2/5] 实现
[阶段 3/5] 编译
[阶段 4/5] 测试
[阶段 5/5] 回归
```

但不得因为进度播报而频繁打断用户。

短操作（预计 10 秒以内）不需要播报。

超过 30 秒的操作（完整测试套件、批量模拟、后台 Agent / Workflow、依赖下载等），额外遵守 §19 的实时反馈三步要求（开始告知、过程播报、结论收尾）。

辅助 Agent 超时降级规则（§19）继续原样适用于 Sprint 执行过程。

---

## 11. Task 最终验收机制（AUTO_ACCEPT 前置检查清单）

每个 Task 自动完成（AUTO_ACCEPT）前必须依次执行：

1. 编译
2. Task 相关测试
3. 完整回归测试
4. Scope Check
5. Git Diff Check
6. 设计文档一致性检查
7. 技术债检查
8. task-state.md 更新

只有全部 PASS：

```text
Task → AUTO_ACCEPT
```

然后继续下一个 Task。

任何一项 FAIL，走 §7 自动修复循环或按例外清单直接 BLOCKED。

---

## 12. Git / Scope 安全闸门

每个 Task 完成后检查：

- 修改文件列表
- 是否存在 Task 范围外修改
- 是否修改冻结设计
- 是否修改数据库结构
- 是否修改 API Contract
- 是否新增未经批准依赖

如果发现范围外修改：

先判断是否属于"完成当前 Task 的必要修改"。

如果是：在简短状态输出中说明原因，继续。

如果不是：立即停止并进入 BLOCKED。

Git 提交策略沿用 §28（v1 §17）：语义化 Commit；未通过验收不创建"完成版"提交。Sprint 内多个 AUTO_ACCEPT 的 Task 可合并为一个 Sprint Commit，由 Checkpoint 验收通过触发提交。

---

## 13. 报告机制

### 13.1 普通 Task：简短状态输出

普通 Task 不再要求输出完整人工验收报告（§21 的完整报告格式保留，仅在 Checkpoint 汇总时作为素材结构使用）。

普通 Task 完成时，只需更新 task-state.md，并输出简短状态：

```text
Task P1-0 AUTO_ACCEPT
Tests: 38/38 PASS
Scope: PASS
Next: P1-1
```

然后自动继续。

### 13.2 Sprint 完成：完整报告

Sprint 完成（到达 Checkpoint）后才输出完整报告，包括：

- Sprint 目标
- 完成 Task
- 修改文件
- 架构变化
- 测试结果
- Scope Check
- 技术债
- 已知问题
- 自动修复记录
- 未解决 Blocker
- 下一 Sprint 建议

---

Task：
P1-1

问题：
……

已尝试：
1. …
2. …
3. …

无法继续原因：
……

方案：
A. …
B. …
C. …

推荐：
B

需要你决定：

━━━━━━━━━━━━━━━━━━━━

执行 Task P0-3

Task 目标
前置依赖
当前项目状态
涉及模块
验收标准

## 18. Task 实现阶段（v1 §5 保留）

AI 开始编码。

要求：

### 18.1 遵循既有架构

不得随意：

更换技术栈
引入新框架
引入基础设施
改变数据库方案
改变 Agent Runtime 模型

如果确实需要修改：

发现问题
 ↓
说明原因
 ↓
提出方案
 ↓
等待用户批准

### 18.2 最小修改原则

优先：

修改完成当前 Task 所必需的代码。

避免：

大规模重构
无关代码优化
提前抽象
提前实现未来功能

### 18.3 不隐藏技术债

如果为了完成 Task 做了临时方案，必须记录 Technical Debt 到 task-state.md 技术债登记表，包括：

问题
原因
当前解决方式
后续建议

## 19. AI 自测与长耗时操作反馈（v1 §6 / §6.1 保留）

Task 完成后，AI 必须自己执行测试。

至少包括：

编译
 ↓
单元测试
 ↓
集成测试（如果适用）
 ↓
Task 专项测试

必须给出实际结果：

mvn test
Tests run: XX
Failures: 0
Errors: 0

禁止只说："测试应该可以通过。"

### 19.1 长耗时操作必须实时反馈进度

凡是预计超过 30 秒的操作（完整测试套件、批量模拟、后台 Agent / Workflow、依赖下载等），AI 必须：

1. 开始时告知正在做什么、预计多久。
2. 过程中主动播报阶段性进度（如"3/10 已完成"、"编译通过，开始跑集成测试"）。
3. 完成或失败后立即给出结论，不允许沉默等待。

禁止：

- 只回复一句"任务运行中"就结束回合。
- 让用户在没有中间信息的情况下长时间等待。

（v2 分级标准见 §10。）

### 19.2 辅助 Agent 超时自动降级（可靠性规则）（v1 §6.2 保留）

当 AI 使用辅助 Agent / 子工作流并行干活时，必须遵守：

1. 任何辅助 Agent 都可能超时或失败——主流程不得无限等待。
2. 启动后台任务时必须设定等待上限；超时未返回即视为失败。
3. 失败后两条路任选其一并明确告知用户：
   - 主对话内降级执行（由 AI 自己补齐该部分工作）；
   - 报告失败原因并询问是否重试。
4. 部分成功时，汇报中必须如实区分"哪些部分完成、哪些部分因失败由主流程补齐"，不得把降级补齐的结果伪装成子 Agent 的产出。

## 20. AI 自检协议（v1 §7 保留）

每个 Task 完成后，AI 必须执行：

### 20.1 功能检查

是否完成 Task 的所有目标。

## 22. 人工验收流程（v1 §9 保留，触发时机【v2 变更】：Checkpoint）

AI 汇报完成后，不代表自动通过。

人类执行：

AI 自测
 ↓
人工黑盒验证
 ↓
结果检查
 ↓
验收

人工验收优先使用黑盒验证，而不是逐行代码审查。

## 23. 不同类型 Task 的验收方式（v1 §10 保留）

### 23.1 基础设施

例如：Spring Boot、SQLite、Maven。

验收：能启动、能测试、能访问。

### 23.2 API

验收：正常请求、异常请求、边界参数、错误响应。

### 23.3 Repository

验收：Create、Read、Update、Delete、Duplicate、Not Found、Transaction。

### 23.4 Agent Runtime

重点验证：正常 Loop、Tool Call、Tool Error、LLM Error、Retry、Timeout、Max Steps、Cancel、Resume。

### 23.5 Simulation

重点验证：固定 Seed、重复实验、结果一致、极端参数、手算 Case、批量模拟。

尤其要求：至少存在一组可以人工计算结果的简单测试 Case。

### 23.6 Tool

验证：合法输入、非法输入、边界输入、权限、异常、返回值。

### 23.7 Config / Diff

验证：v001 → Proposal → Approval → v002。

并检查：旧版本不能被破坏、Diff 正确、Reject 正确、Rollback 正确。

### 23.8 SSE

验证：连接 → 收到事件 → 多个事件 → 断线 → 重新连接 → 事件补发。

### 23.9 AI Agent

最终必须进行真实任务验收，不能只依赖单元测试。

## 24. 三层验收模型（v1 §11 保留）

整个项目采用三层验收。

Level 1：代码验收——编译、测试、静态检查。回答："代码能不能工作？"

Level 2：功能验收——API、UI、数据库、Agent、Simulation。回答："功能是不是按照设计工作？"

Level 3：产品验收。回答："这个东西到底有没有用？"

例如 AI Game Designer：

输入"Crit Build 明显过强" → AI 自主分析 → 模拟 → 发现问题 → 提出方案 → 人工批准 → 修改 → 重新模拟 → 达到目标 → 生成报告。

只有 Level 3 通过，AI Game Designer 才算真正完成。（Level 3 仍在项目最终验收时执行，不因 v2 而下放给 AI。）

## 25. 重要 Task 必须进行"挑战测试"（v1 §12 保留）

对于核心模块，不能只测试正常情况。必须主动制造失败。

例如 Agent：Tool 返回错误、LLM 超时、LLM 返回非法 Tool Call、Agent 无限循环、Token 超预算、用户取消、进程中断。

Simulation：HP = 0、Attack Speed = 0、Crit = 100%、Crit = -1%、Enemy = 0、Simulation Count = 1、Simulation Count = 100000。

Config：非法字段、不存在字段、类型错误、范围错误、并发修改。

## 30. 并行开发原则（v1 §19 保留）

任务树虽然允许并行（如 P0-3、P0-4、P4-0），但如果只有一个 AI Coding Agent：默认串行。

只有满足以下条件才并行：

模块完全独立
API Contract 已冻结
不会修改同一核心文件
验收成本不会显著增加

否则优先串行。

## 31. AI Token 使用原则（v1 §20 保留）

本项目拥有较充足的 DeepSeek Token，因此优先让 AI 多思考、多测试、多验证，而不是减少 Token。

允许 AI：多轮自检、自动运行测试、生成测试数据、运行大量 Simulation、分析实验结果、检查代码。

但禁止：为了消耗 Token 而生成无意义的文档和抽象。

## 32. Agent 开发特别规则（v1 §21 保留）

Agent 本身是本项目最重要的模块。

必须记录：Task、Run、Step、LLM Call、Tool Call、Tool Result、Event。

任何 Agent 行为必须能够追踪。

核心原则：Agent 做了什么，为什么做，调用了什么工具，得到了什么结果，最终为什么停止，都必须可以从 Run Trace 中还原。

## 33. Tool 开发特别规则（v1 §22 保留）

每个 Tool 必须：输入明确、输出明确、Schema 明确、错误明确、权限明确。

Tool 不应该偷偷修改其他系统状态。

特别是 modify_game_config 必须经过：

Proposal
 ↓
Approval
 ↓
Apply

## 34. Simulation 开发特别规则（v1 §23 保留）

Simulation 必须满足：

可重复：相同 Config + 相同 Seed + 相同 Simulation Version = 相同结果。

可比较：Config v001 vs Config v002。

可解释：不能只返回 Win Rate = 57%，必须能够提供足够的数据解释为什么。

## 35. AI Game Designer 最终验收标准（v1 §24 保留）

第一阶段最终必须完成：

用户提出设计问题 → Agent 创建 Run → 读取游戏配置 → 运行实验 → 分析实验 → 提出修改方案 → 生成 Change Proposal → 用户 Approval → 创建新 Config Version → 重新实验 → 比较实验 → Agent Evaluate → 完成 → 生成最终设计报告

并且整个过程可以在中台完整追踪。

## 36. MVP 完成定义（v1 §25 保留）

AGL 第一阶段只有同时满足以下条件才算完成：

技术层：Spring Boot 正常运行、React 正常运行、SQLite 正常运行、Agent Runtime 正常运行、LLM Gateway 正常运行、Tool Registry 正常运行、Simulation 正常运行、SSE 正常运行。

功能层，AI 能：读取游戏配置、运行实验、分析实验、提出修改、等待人工批准、修改配置、再次实验、比较结果、输出报告。

产品层：能够完成"发现一个游戏平衡问题 → AI 通过实验分析 → 提出修改 → 人工批准 → 验证修改效果"完整闭环。

## 37. 每次 Sprint 启动的固定指令（v1 §26 更新）

以后向 AI Coding Agent 下达任务时，统一使用：

"开始执行 P1 Sprint"

或单个 Task 场景：

"执行 Task XXX"

严格按照 AGL《AI 协作开发工作流 v2》执行。

要求：

1. 只执行当前 Sprint / Task 范围内的内容。
2. 不提前实现后续 Sprint。
3. 不擅自修改架构。
4. 每个 Task 完成后运行编译、相关测试与完整回归测试。
5. 执行 Task 自检协议（§20）。
6. 维护 task-state.md。
7. 普通 Task 用简短状态汇报（§13.1），自动进入下一个 Task。
8. 检查是否存在范围外修改，必要时进入 BLOCKED。
9. 到达 Checkpoint 或 BLOCKED 时才停止等待人工。
10. Checkpoint 时输出完整 Sprint 报告。

不要因为单个普通 Task 完成就停止等待验收。

## 38. 人工验收固定指令（v1 §27 保留）

AI 完成 Sprint 后，人类可以使用：

执行 AGL Task 验收。

请：

1. 对照 Task 原始目标逐项检查。
2. 对照验收标准逐项检查。
3. 检查自动化测试。
4. 检查是否存在范围外修改。
5. 检查是否违反架构设计。
6. 检查是否引入不必要依赖。
7. 检查异常和边界情况。
8. 给出需要我手动执行的最少验证步骤。
9. 最终给出：PASS / CONDITIONAL PASS / FAIL

## 39. 验收等级（v1 §28 保留）

PASS：完全符合要求。可以进入下一个 Sprint。

CONDITIONAL PASS：基本完成，但存在可接受技术债、非核心小问题、后续可以处理的问题。可以继续，但必须记录技术债。

FAIL：存在核心功能错误、架构违反、数据错误、无法复现、测试失败、MVP 边界被破坏。必须修复后重新验收。

## 40. AI 不得自行改变架构（v1 §13 保留）

以下行为必须经过人工批准：

更换数据库
更换框架
引入新基础设施
修改核心 Agent Runtime
修改 Tool Contract
修改 API Contract
修改数据模型
改变任务依赖关系
扩大 MVP 范围

AI 可以提出建议，但不能自行执行。

## 41. 设计文档优先级（v1 §16 保留）

如果不同文档发生冲突，优先级：

1. 当前用户明确要求
2. 当前阶段 MVP 定义
3. 01_AI游戏策划Agent（需求文档）
4. 00_总架构与中台设计
5. Task Tree
6. AI 自己的推断

**同一文档内部：具体规范优先于摘要描述。** 明确的 DDL / API Contract / 状态机定义 / 接口签名，优先于章节标题、任务树表格、概述文字中的计数或概括。发现摘要与具体规范不一致时，以具体规范为准，并回写修正摘要（修正需在汇报中注明）。

AI 不得因为"自己觉得更好"而覆盖用户明确要求。

## 42. 最重要的原则（v1 §29 更新）

整个项目遵循：

小步开发，小步验证，持续积累——但验证的重心从"每 Task 人工"转移到"每 Task 自动 + 每 Sprint 人工"。

不要追求一次让 AI 写完整个平台。

而应该以 Sprint 为单位：

Task → 实现 → 测试 → AUTO_ACCEPT → Task → 实现 → 测试 → AUTO_ACCEPT → ... → Checkpoint 验收 → Commit → 下一个 Sprint

最终让几十个小的、确定正确的 Task 组合成一个真正可运行的 AI Game Lab，而 AI 以 Sprint 为单位自主连续完成它们，只在真正需要人的地方停下来。
